Sankalp API

One endpoint, one key, one bill. Send a request to Sankalp and an answer comes back - the models behind it are ones we operate, served through this API.

What this is

Sankalp is an API in front of the models we operate. You call one endpoint; we take care of the key, the limits, the bill and the record of what happened. The model names below are our routes, not engines - the engine behind a name may change, and the API stays the same.

That is why there is one place to look for what you spent: every request records the route that answered it and the tokens it used, so the console's numbers and your invoice are the same numbers counted once.

Quickstart

Make a key in the console, then send this. The key is the only thing you have to keep secret.

curl https://sankalp.indoworkspace.in/v1/chat/completions \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "sankalp-standard",
    "messages": [{"role": "user", "content": "Say hello in one sentence."}]
  }'

The first request of a new account is free to try; a failed request is never charged.

Authentication

Every request carries a key in a header, as a bearer token. Two kinds of key exist, and they are not interchangeable:

KeyWhat it does
sk_live_…Answers requests and spends from the wallet.
sk_test_…Answers requests, never spends, never appears in live usage.

Keys are shown once when they are made. What we keep is a hash, so a key that is lost cannot be shown again - revoke it and make another.

The endpoint

POST /v1/chat/completions

FieldTypeWhat it does
modelstringOne of the five routes below.
messagesarrayrole and content, oldest first. A system message sets the behaviour.
temperaturenumber0 to 2. Lower is steadier.
max_tokensnumberThe longest answer you will accept.
streambooleanWords as they are written, instead of all at once.

The response

{
  "id": "req_8f21c4",
  "model": "sankalp-standard",
  "choices": [{
    "message": {"role": "assistant", "content": "Hello! How can I help?"}
  }],
  "usage": {"input_tokens": 12, "output_tokens": 8}
}

The usage block is what the bill is made from. It is the same number the console shows, so a disagreement between them is a bug, not a rounding.

Streaming

With "stream": true the answer arrives as server-sent events, one piece at a time, ending with data: [DONE]. The usage block is in the last event before that.

data: {"delta": "Hello"}
data: {"delta": " there"}
data: {"usage": {"input_tokens": 12, "output_tokens": 8}}
data: [DONE]

Errors

StatusWhat happenedWhat to do
400The request is malformed.Read the message; it names the field.
401The key is wrong or revoked.Make a new key.
402The wallet is empty.Top up, or lower the spend threshold.
429A limit was hit.Wait for Retry-After and try again.
500Something on our side failed.Retry once; if it repeats, send us the request id.

Rate limits

Limits belong to the key, so one runaway script cannot stop your other keys. Every response carries the state of the window:

X-RateLimit-Limit: 60
X-RateLimit-Remaining: 12
X-RateLimit-Reset: 34

When a limit is reached the answer is 429 with Retry-After in seconds. The console's Rate limits screen lists every refusal with the limit that caused it.

Webhooks

Point an HTTPS address at us and we call it when something finishes, with a signature your server can check. The body carries ids and counts, not the conversation.

{
  "id": "evt_2f91c4a8",
  "type": "chat.completed",
  "data": {
    "request_id": "req_8f21c4",
    "model": "sankalp-standard",
    "tokens": {"input": 412, "output": 96}
  }
}

Events: chat.completed, chat.failed, wallet.low, key.created, key.revoked. A delivery is retried with a growing gap for a day.

Help

If a request fails and the reason is not in the table above, send us the request id from the console's Logs screen. That id is the whole story of one call, and it saves a round of questions.
